PulseFeed is a three-channel vacuum, pulsation and motor controller built on an M5Stack CoreS3. Rate and ratio are held by a dedicated real-time task, so the pulse stays exactly where you set it whether the screen is idle or six people have the dashboard open.

How it works

Three outputs, one clock, no drift

Vacuum, pulsation and motor are independent. Changing one never interrupts the others, and none of them are at the mercy of whatever the screen or the network happens to be doing.

CH1 · GPIO 5Vacuum 0–100%

Duty-windowed solenoid or a proportional valve on hardware PWM. A first-order response model with a tunable time constant, so the ramp behaves the same under any load.

CH2 · GPIO 6Pulsation 0, 30–400 PPM · ratio 30–70%

The heart of it. Rate and on:off ratio are both set independently. Or hand the channel to one of 30 rhythm patterns, adjustable in 10 custom slots.

CH3 · GPIO 7Motor 0–100% in 5% steps

20 kHz hardware PWM with a configurable soft start, so the motor ramps instead of slamming to full and it runs above the audible range.

Timing that holds

The channel engine runs at 1 kHz in its own high-priority task on its own core. Repainting the screen, serving the dashboard and writing the SD log all happen underneath it and cannot stretch a pulse.

Proven, not asserted

The engine is plain C++ with no hardware dependencies, so the same code the device runs is exercised by 89 host tests — pulse counts at five rates, measured duty at five ratios, and every safety interlock.

Records what happened

Every start, stop, setting change and interlock trip lands in a daily CSV on the SD card, queued from a ring buffer so the card is never touched from a control path. Load it in the built-in report page.

Remote access

Share it without handing over the machine

The bridge is a reverse proxy that sits in front of the controller with its own auth, its own rate limiting and an audit log. It runs in a mode that caps what remote clients can do — and the default mode cannot start anything.

A ladder, not a switch

ModeReadStopTurn downStart
readonly✓✓——
supervise✓✓✓—
control✓✓✓—

Stop and e-stop are permitted in every mode including read-only. If remote access can see a problem, it must always be able to stop it.

Point the tunnel at the bridge

# bridge in front of the device
./pulsefeed-bridge.py \
  --target http://192.168.13.50 \
  --listen 127.0.0.1:8443 \
  --mode readonly \
  --audit /var/log/pulsefeed/audit.jsonl

# cloudflare tunnel in front of the bridge
cloudflared tunnel run pulsefeed

Ready-made configs for Cloudflare Tunnel, nginx, Caddy and systemd ship in bridge/. No port forwarding required.

Safety

What the software guarantees — and what it can't

Interlocks in the firmware

  • Outputs driven to a safe state before anything else initialises
  • E-stop cuts all three channels on the press, then latches
  • Deadman: a stalled supervisor stops the machine within 2.5 s
  • Configurable maximum run time, on by default
  • Optional stop-on-network-loss for unattended supervision
  • Every setting clamped on load, on write and before save

Read this before you rely on it

  • This is prototype control software, not a certified safety system. It has no third-party assessment and no redundancy.
  • Software interlocks cannot protect against a shorted driver, a welded relay or a failed MOSFET. Anything that must fail safe needs a hardware interlock that does not go through the microcontroller.
  • The output polarity in pf_config.h reproduces the previous firmware's behaviour and has not been verified against a physical board. Confirm it with the channels disconnected before you connect a load.
  • Remote access is convenience, not supervision. Do not run a machine nobody is standing next to.
