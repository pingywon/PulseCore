Architecture

The firmware is split so that the part which must keep time has no dependency on the parts that can block.

firmware/pulsefeed/
  pf_core.h/.cpp     portable engine: settings, rhythm compiler, channel
                     scheduler, JSON writer. No Arduino headers at all,
                     which is what lets tests/ compile it on a host.
  pf_rhythms.cpp     built-in pattern table
  pf_config.h        pins, board wiring, build-time policy
  pf_hal.h/.cpp      GPIO, LEDC PWM, monotonic clock
  pf_app.h/.cpp      application state + the single command surface
  pf_ui.h/.cpp       touchscreen: layout table, canvas rendering, touch
  pf_net.h/.cpp      WiFi, setup AP, mDNS, captive portal, async scan
  pf_api.h/.cpp      HTTP server, REST API, auth, rate limiting
  pf_log.h/.cpp      lock-free queue -> batched SD writes
  pf_store.h/.cpp    NVS with change-only writes
  pf_web.h           GENERATED: gzipped web UI (tools/build_web.py)
  pulsefeed.ino      setup(), loop(), the engine task

Tasks

TaskCorePriorityDoes
pf_engine1191 kHz tick; the only writer of the output pins
loopTask11UI, touch, HTTP, DNS, SD flush, persistence
wifi / lwIP023Arduino default

loop() calls engine.feed() every pass. If it stops doing so for 2.5 s the engine stops the machine on its own and records STOP_WATCHDOG. That is the deadman: a wedged UI or network stack cannot leave a channel energised.

On settings races. The engine task reads Settings while loop() may be writing it. That is deliberate and safe: every field is independently clamped before it is stored, so any interleaving of old and new fields is itself a valid configuration. Only the compiled rhythm patterns need real care, and recompileCustom() takes a pattern off the air before rebuilding it.

Channels & limits

ChannelPinRangeDrive
CH1 vacuumGPIO 50–100%Duty window (default 1000 ms) or LEDC PWM at 200 Hz
CH2 pulsationGPIO 60, 30–400 PPM
ratio 30–70%		Discrete, always. A pulsator is bang-bang.
CH3 motorGPIO 70–100%, 5% stepsDiscrete or LEDC PWM at 20 kHz + soft start
spareGPIO 8—Held de-energised, never exposed

Rhythm ids

  • 0 — off; CH2 follows the PPM/ratio setting
  • 1–30 — built-in patterns
  • 32–41 — the ten recordable/adjustable custom slots. Each can start from a tap recording or a copy of any built-in (POST /api/v1/custom action=seed&from=<builtin id>), then be renamed and re-saved.

Notation: . is one unit on then one off, - is three on then one off, and a space adds one more unit of rest to the step before it. One unit is 250 ms at 100% speed. Patterns are compiled to explicit milliseconds once, on change, never re-parsed while playing.

REST API v1

Every response is JSON. Every mutation is POST with an application/x-www-form-urlencoded body and an X-PF-Token header.

EndpointAuthPurpose
GET/api/v1/metaopen Version, limits, the built-in rhythm table. Fetched once by the browser.
GET/api/v1/healthopen Liveness probe for a proxy. Reveals nothing about machine state.
POST/api/v1/authopen pin= → {token}. Rate limited, locks out after 5 failures.
GET/api/v1/statetoken Full machine state. This is what the dashboard polls.
POST/api/v1/controltoken action=start|stop|estop|release|clear
POST/api/v1/settingstoken vac ppm ratio motor ramp motorSoftMs runLimitMin backlight dark — any subset
POST/api/v1/rhythmtoken id= and/or speed=, or fav=1..3
POST/api/v1/customtoken slot=1..10 + action=arm|down|up|stop|save|clear|play|rename|seed. seed also takes from=<builtin id> and copies that preset's timing into the slot as an editable tap-recorder pattern.
GET/api/v1/wifi/scantoken Starts an async scan and returns what is cached. Poll while scanning is true.
POST/api/v1/wifi/jointokenssid= pass=
GET/api/v1/logstokenList the CSV files on the card
GET/api/v1/logs/gettoken or ?t=file=YYYY-MM-DD.log
POST/api/v1/systemtokenaction=save|reboot|newpin

Example

TOKEN=$(curl -s -X POST -d "pin=123456" \
  http://pulsefeed.local/api/v1/auth | jq -r .token)

curl -s -X POST -H "X-PF-Token: $TOKEN" \
  -d "ppm=120&ratio=60&vac=70" \
  http://pulsefeed.local/api/v1/settings

curl -s -X POST -H "X-PF-Token: $TOKEN" \
  -d "action=start" http://pulsefeed.local/api/v1/control

curl -s -H "X-PF-Token: $TOKEN" \
  http://pulsefeed.local/api/v1/state | jq

Authentication

  • A six-digit PIN is generated on first boot and stored in NVS. It is shown on the controller's Network screen and nowhere else.
  • POST /api/v1/auth exchanges it for a bearer token, good for 12 hours. Up to four concurrent sessions.
  • Five wrong PINs lock the endpoint for 60 seconds.
  • Mutations require the token in the X-PF-Token header. A cross-origin form cannot set a custom header, so this is the CSRF defence as well. Tokens are never accepted from a cookie.
  • File downloads accept ?t= because the browser navigates to them directly. That is the only exception, and it is GET-only.
Turning auth off. Settings has a switch for it. It exists for a bench with no network, and it is the wrong choice anywhere else. With auth off, anyone who can reach the port can start the machine.

Board wiring and build policy live in pf_config.h.

ConstantDefaultMeaning

Output polarity is unverified. The default reproduces the previous firmware's electrical behaviour exactly, because guessing wrong here energises channels. Confirm against your driver board with the loads disconnected before changing PF_OFF_MODE or enabling PWM on a channel — PWM has no high-impedance state and must drive the pin.

Session logs

With an SD card present, one CSV per day at /log/YYYY-MM-DD/YYYY-MM-DD.log:

ms,time,event,vacTarget,vacActual,ppm,ratio,motor,rhythmId,
running,solVac,solPulse,solMotor,estop,heap

Events carry their origin: start(screen), set-ppm(web), stop(auto). Records are queued and flushed once per second in a single open/close, so nothing on a control path ever waits on the card. If the queue fills, the drop is counted and reported in state.sys.logDropped rather than blocking.

Open /stats on the device for the report view, or drop a file into that page from a card reader.

Remote access

Use bridge/pulsefeed-bridge.py. It is a reverse proxy with its own auth, per-client rate limiting, an audit log and a mode ladder that caps what remote clients can do.

./pulsefeed-bridge.py --target http://192.168.13.50 \
    --listen 127.0.0.1:8443 --mode readonly \
    --device-pin 123456 \
    --audit /var/log/pulsefeed/audit.jsonl

--device-pin is exchanged for a token once at startup, so visitors never see the device PIN. Point Cloudflare Tunnel, nginx or Caddy at the bridge — never at the device. Configs are in bridge/tunnel/.

Simulator

tools/build.sh sim
./dist/pulsefeed-sim --port 8080 --pin 246813

Links the same pf_core.cpp the firmware does, runs the engine at 1 kHz in a thread, and serves the same dashboard and the same API. Useful for reviewing the UI, developing against the API, and testing the bridge without a device on the bench.

Test suite

tools/build.sh test

89 assertions against the exact engine the firmware ships, including:

  • pulse counts at 30, 60, 120, 240 and 400 PPM, within one pulse of exact
  • measured on-phase duty at 30/40/50/60/70% ratio, within 0.5%
  • pattern position stays exact across 24 simulated hours at 300% speed (the 32-bit overflow the previous firmware had)
  • e-stop de-energises on the same tick and refuses a restart while latched
  • deadman and run-limit both stop the machine and record the reason
  • vacuum ramp within 5% across a 10× change in tick rate
  • a stopped engine energises nothing at any setting
  • JSON escaping of control characters and invalid UTF-8

Safety notes

This is prototype control software. It is not certified, not redundant, and not assessed by anyone. Software interlocks cannot protect against a shorted driver, a welded relay or a failed MOSFET. Anything that must fail safe needs a hardware interlock that does not pass through the microcontroller.

What the firmware does guarantee:

  • Output pins are driven to their de-energised state before any other initialisation, closing the power-on window.
  • E-stop calls the HAL directly — the pins are cut before the model is updated and before anything is logged.
  • A stopped or latched engine returns all-off unconditionally, ahead of every other computation in tick().
  • The run limit defaults to 60 minutes. Setting it to 0 disables it, which is an explicit choice rather than the default.
